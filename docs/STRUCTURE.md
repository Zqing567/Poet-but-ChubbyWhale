# 项目组织方法：叙事 × 制作 × 经验

## 为什么不用单一“视觉/听觉”文件夹

用户的《将进token视频拆解.canvas》把作品按“视觉（人物、场景、文字）/听觉（BGM、音效、配音念白）”划分，并强调人物内在身份、性格、情绪与服装动作、场景要协调；这份图适合创意分析。另一份 Codex Mermaid 把 87.1 秒视频描述为“声音骨架 → 第一幕 GPU 海崖 → 第二幕曲水流饭 → 片尾延续 → 合成导出”，并把诗句字幕、想象气泡和动态表情视为贯穿两幕的视觉叠加层。这份图适合解释实际生产顺序。

**这两种分类都应该保留，但分别用于不同问题，而不应二选一。**

| 视角 | 单元 | 什么时候看 |
| --- | --- | --- |
| 叙事视角（what） | 第一幕海崖、第二幕曲水、片尾、L01～L12 | 修改剧情、找一个梗出现在哪句、做分镜 |
| 技术视角（how） | 角色/场景资产、声音、字幕、动态叠加、时间轴、合成与质检 | 修改某一种效果、寻找复用代码、复现制作 |
| 资产与决策（why） | 来源、候选/最终版本、Prompt、授权、失败/有效经验 | 开源复现、以后拍新视频时复用 |

文件系统**按项目优先、模块其次**，避免两个场景各自产生不兼容的字幕与声音子工程。所有要素在一个素材索引中以稳定的 asset_id 互相关联，不能只有零散文件名。

## 跨项目结构

- `projects/<slug>/`：一部已制作作品，拥有独立故事、编辑工程、方法文档、发布记录。
- `shared/`：以后经验证适用于第二部及更多作品的公共能力。第一部成功不代表模块就足够通用，**不要过早把专用代码抽成库**。
- `docs/`：统一命名、许可、迁移与贡献规则。
- `tools/`：资产来源与迁移检查、通用仓库守卫。
- 以后可建立 `projects/next-poem/`，而不在 `jin-token` 下开另一期。

## 《将进 token》结构

`projects/jin-token/editor/src/` 保留作者已经完成的 Remotion v11 制作代码及最终配置信息。它对应制作系统，不是按十二句拆成十二个独立工程。

`projects/jin-token/docs/` 面向人解释实际做法，`projects/jin-token/assets/` 提供依赖声明和权利状态，`projects/jin-token/release/` 面向正式交付物。

**一个效果对应四个可追踪点**：故事中的哪句/场景、代码入口、所需资产 ID、最终能验证的证据文件。比如 L01 token 落铁盆 → 第一幕 TokenRain → upper-half/metal-token-v1.png → 成片对应时间段及渲染检查。这样重新制作只需改该模块，不需要翻完整段日志。

## 项目拆解不是“拆得越细越专业”

推荐按**可独立替换且有清晰输入输出**划分。诗文/时序是共享合同；场景与角色是图像资产；气泡与字幕是独立合成层；朗诵和配乐是音频输入；Remotion 做整片编排；最后验证是单独的交付步骤。

经验材料也必须区分“曾经建议过”“试验中”“作者选定”“最终成片采用”。计划文件不能假装为最终经验。
